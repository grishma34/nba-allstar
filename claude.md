# claude.md

Instructions for Claude Code working in this repository.

---

## Context

This is a **university assessment**. The code is not the deliverable on its own — the
student must defend every design decision in a 10-minute live Q&A, without reading
the code on screen to find answers.

The marking rubric explicitly penalises AI-generated implementations the student
cannot explain. Two rubric bands, quoted:

> **Failed (0%):** "an implementation is generated by AI tools and the student cannot
> demonstrate BASIC understanding of the model structure, algorithm, and key components"

> **Partially Failed (25%):** "if a student needs to read through the code/comments
> on-site during the presentation to find how many channels are used in a layer/loss
> function definition"

**Therefore: optimise for the student's understanding, not for elegance, brevity or
cleverness.**

---

## Hard rules

1. **Never import a machine learning model.** No `sklearn.linear_model`, no
   `statsmodels`, no `scipy.optimize` for fitting. Sigmoid, loss, gradients and the
   update loop are hand-written with numpy.

2. **Comment the *why*, not the *what*.** Assume the reader is competent in Python
   but shaky on the maths. Name every formula being implemented. Explain what each
   term means and why it is there.

3. **Prefer explicit over concise.** A five-line loop that reads clearly beats a
   one-line comprehension. Intermediate variables with meaningful names are good.
   This code will be read aloud under pressure.

4. **No silent design decisions.** If a choice arises — a threshold, a default, a
   filter value — stop and ask. Do not pick a reasonable default and move on. Every
   decision must be traceable to `docs/DATA_DECISIONS.md`.

5. **Ask before adding a dependency.** The permitted set is numpy, pandas,
   matplotlib. Anything else needs a reason.

6. **No scope creep.** No AWS, no web UI, no additional models, no extensive EDA.
   The specification actively warns against the last one.

## Commenting standard

Every function gets a docstring covering:
- what it computes
- the mathematical formula, if it implements one
- what each parameter is
- what it returns and what the values mean

Example of the expected density:

```python
def log_loss(y_true, y_pred, eps=1e-15):
    """
    Binary cross-entropy loss.

        L = -(1/n) * Σ [ y·log(ŷ) + (1-y)·log(1-ŷ) ]

    Reads as: for each sample, if the true label is 1 we are penalised by
    -log(ŷ) — small when ŷ is near 1, exploding as ŷ approaches 0. If the true
    label is 0, the second term applies instead and mirrors it.

    The practical consequence is that being CONFIDENTLY WRONG is punished far
    more heavily than being uncertain. Predicting 0.99 on a negative sample
    costs about 4.6; predicting 0.6 costs about 0.9.

    eps clips predictions away from exactly 0 or 1, because log(0) is -inf and
    would make the loss undefined.

    Args:
        y_true: ndarray of 0/1 labels, shape (n,)
        y_pred: ndarray of predicted probabilities in (0,1), shape (n,)
        eps:    clipping bound for numerical stability

    Returns:
        float — mean loss across all samples. Lower is better. 0 is perfect.
    """
```

## When implementing the maths

For each of sigmoid, log loss and the gradients:

1. State the formula in the docstring
2. Implement it in a form that visibly matches the formula
3. Explain in comments why each term exists
4. Note any numerical-stability handling and why it is needed

For the gradient functions specifically, include the derivation in the docstring —
at least the chain-rule steps. The student needs to be able to reproduce it on a
whiteboard.

---

## Working style

- **Small commits, one concern each.** Meaningful messages.
- **Build in the order set out in `tasks.md`.** Do not jump ahead.
- **After each module, stop.** Summarise what was written and flag anything the
  student should be able to explain but might not yet.
- **Flag knowledge gaps actively.** If something is implemented that the student is
  unlikely to fully understand, say so and suggest an entry for
  `docs/KNOWLEDGE_GAPS.md`.

---

## What "done" looks like for a module

- Runs
- Has a test, where testable
- Every function has a docstring at the density shown above
- Any decision it embodies is recorded in `docs/DATA_DECISIONS.md`
- The student can explain, without looking: what it does, why it exists, and why it
  was built this way rather than another way

If the last point is not true, the module is not done.
